Job {
  jobId: String           (LinkedIn numeric or "naukri-{id}")
  title: String
  company: String
  location: String
  postedTime: String      (ISO8601 or relative text)
  url: String
  description: String
  source: String          ("linkedin" or "naukri")
  firstSeen: DateTime
  lastUpdated: DateTime
}

JobFilter {
  keywords: List<String>
  companyWhitelist: List<String>
  companyBlacklist: List<String>
  location: String?
  minDaysOld: int?
}

MonitoringSession {
  scheduledFor: DateTime
  startedAt: DateTime
  finishedAt: DateTime
  status: String
  jobsFound: int
  newJobs: int
  error: String
}

================================================================================
DATABASE SCHEMA (3 NEW TABLES)
================================================================================

jobs
├─ job_id (PRIMARY KEY)
├─ title, company, location
├─ posted_time, url, description
├─ source ("linkedin" or "naukri")
├─ first_seen, last_updated
└─ Indexes: source, first_seen, company

job_filters
├─ id (PRIMARY KEY)
├─ name (UNIQUE)
├─ keywords (JSON array)
├─ company_whitelist (JSON array)
├─ company_blacklist (JSON array)
├─ location, min_days_old
└─ is_active, created_at

monitoring_sessions
├─ id (PRIMARY KEY)
├─ scheduled_for (UNIQUE)
├─ started_at, finished_at
├─ status ("pending", "ok", "failed")
├─ jobs_found, new_jobs, error
└─ Index: scheduled_for

PORTING ANALYSIS - CODE REUSABILITY
================================================================================

FROM AUTOMATE PYTHON REPO:

linkedin.py (284 lines)
  ├─ HTML Parsing → Port to Dart (html package)
  ├─ CSS Selectors → BeautifulSoup → Dart html.query()
  ├─ Retry Logic → Direct port
  └─ Porting: ⭐⭐ MEDIUM COMPLEXITY

naukri.py (232 lines)
  ├─ HTML Parsing → Port to Dart (html package)
  ├─ Playwright/JS → HTTP only (MVP limitation)
  ├─ Fallback JSON-LD → Direct port
  └─ Porting: ⭐ LOW COMPLEXITY (HTTP only)

database.py (147 lines)
  ├─ SQLite operations → sqflite (direct mapping)
  ├─ Job dataclass → Dart model
  ├─ INSERT OR IGNORE → SQL equivalent
  └─ Porting: ⭐ LOW COMPLEXITY

monitor.py (247 lines)
  ├─ poll_once() logic → Direct port to Dart
  ├─ Filter engine → Direct port (pure function)
  ├─ Retry loop → Adapt to Futures/async
  └─ Porting: ⭐ LOW COMPLEXITY

notifications.py (110 lines)
  ├─ termux-notification CLI → flutter_local_notifications
  ├─ Vibration/TTS → Platform channels or skip
  ├─ Telegram → Skip (mobile only)
  └─ Porting: ⭐ LOW COMPLEXITY

scheduler.py (94 lines)
  ├─ Signal handling → Dart event handling
  ├─ While loop → WorkManager periodic task
  ├─ Session recording → Direct port
  └─ Porting: ⭐⭐ MEDIUM COMPLEXITY (WorkManager)

OVERALL REUSABILITY: ✅ 85% CODE COMPATIBLE

================================================================================
NON-FUNCTIONAL REQUIREMENTS
================================================================================

Scalability:
  • Support 10,000 jobs in local database
  • Handle 100+ jobs per polling cycle
  • 20 concurrent API requests (graceful degradation)
  • Batch insert optimization

Reliability:
  • Graceful network failure handling
  • Retry logic with exponential backoff (3 retries)
  • Database WAL mode for integrity
  • Service auto-restart on crash
  • Backup/restore capability

Security:
  • No sensitive data in logs
  • No hardcoded credentials
  • Public API only (no login required)
  • Local storage only (no cloud sync)
  • User consent for background service

Privacy:
  • Jobs stored locally only
  • User can clear all data
  • Optional analytics (user opt-in)
  • No behavior tracking
