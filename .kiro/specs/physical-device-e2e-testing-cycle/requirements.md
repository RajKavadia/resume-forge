# Requirements Document

## Introduction

This feature defines a repeatable, runnable Flutter Android end-to-end cycle on a designated physical device. The cycle shall launch the checked-out application, inject a runtime NVIDIA API key through the application's UI text field, enter tailoring input, exercise the live NVIDIA API exactly as the application does on the device, and verify that the application generates a tailored resume. The cycle shall not require application source-code changes. Screen recordings, supplemental evidence, supplemental validation tests, and a final verdict are optional.

## Glossary

- **E2E_Test_Cycle**: One execution of the physical-device scenario from device preflight through tailored-resume verification.
- **Designated_Device**: The approved physical Android device selected for the cycle and addressable through ADB.
- **ADB**: Android Debug Bridge used to install, launch, inspect, control, and collect optional evidence from the Designated_Device.
- **Accessibility_XML**: An Android accessibility hierarchy dump describing visible UI nodes, bounds, text, content descriptions, and interaction state.
- **Flutter_Semantics**: Accessibility and semantic information exposed by Flutter widgets for identifying controls and visible application state.
- **Input_Automation**: Actions that tap, scroll, drag, or enter text on the Designated_Device through the application UI.
- **Runtime_API_Key**: A test NVIDIA credential entered into the application's runtime API-key text field during the cycle.
- **Live_NVIDIA_API**: The configured NVIDIA API endpoint reached by the running application using the Runtime_API_Key, without a mock, stub, fixture, or cached response replacing the request.
- **Tailored_Resume**: Resume output generated by the application after processing the supplied resume context and job description through the Live_NVIDIA_API.
- **Resume_Marker**: A scenario-defined textual or structural indicator expected in the generated resume, such as a heading, skills section, experience section, or job keyword.
- **Test_Run_Record**: A record of device identity, scenario inputs by non-secret identifiers, step outcomes, and generated-artifact metadata for one cycle.
- **Supplemental_Evidence**: Optional recordings, screenshots, accessibility dumps, logcat output, network diagnostics, action traces, or other artifacts beyond the mandatory cycle result.

## Requirements

### Requirement 1: Physical-device preflight

**User Story:** As a release engineer, I want the cycle to verify its physical-device prerequisites, so that the scenario runs against the intended Android device.

#### Acceptance Criteria

1. WHEN an E2E_Test_Cycle starts, THE E2E_Test_Cycle SHALL identify the Designated_Device through ADB and record the device identifier, Android version, device model, screen dimensions, application package, and test-run identifier.
2. IF the Designated_Device is unavailable, unauthorized, offline, or does not match the configured device identity, THEN THE E2E_Test_Cycle SHALL record the preflight failure and stop before application interaction.
3. WHEN the application is launched for an E2E_Test_Cycle, THE E2E_Test_Cycle SHALL record the launch result and application build identity when available.
4. IF the application cannot be launched on the Designated_Device, THEN THE E2E_Test_Cycle SHALL record the launch failure and stop before tailoring input.

### Requirement 2: Runtime API-key injection

**User Story:** As a release engineer, I want to provide the NVIDIA credential through the application UI, so that the cycle matches device use and avoids code or fixture-based credential injection.

#### Acceptance Criteria

1. WHEN the application displays the runtime API-key control, THE Input_Automation SHALL locate the UI text field using Flutter_Semantics, Accessibility_XML, or another observable accessibility representation when available.
2. WHEN the Runtime_API_Key is available, THE Input_Automation SHALL enter the Runtime_API_Key into the application's UI text field during the E2E_Test_Cycle.
3. THE E2E_Test_Cycle SHALL keep the Runtime_API_Key out of Test_Run_Record content and Supplemental_Evidence.
4. IF the runtime API-key text field is absent or cannot accept the Runtime_API_Key, THEN THE E2E_Test_Cycle SHALL record the injection failure and stop before submitting the tailoring request.

### Requirement 3: Accessibility-informed device interaction

**User Story:** As a release engineer, I want the cycle to discover controls from observable semantics, so that interactions remain tied to the actual device UI.

#### Acceptance Criteria

1. WHEN a required control is available in Flutter_Semantics or Accessibility_XML, THE Input_Automation SHALL identify the control using its semantic label, visible text, content description, role, or bounds before using coordinate-based interaction.
2. WHEN a required control is not exposed through Flutter_Semantics or Accessibility_XML, THE Input_Automation SHALL use a documented device-coordinate or other observable fallback for that control.
3. WHEN the E2E_Test_Cycle executes the scenario, THE Input_Automation SHALL perform the required taps, text entry, scrolling, and other interactions needed to submit tailoring input and reach generated resume output.
4. THE E2E_Test_Cycle SHALL execute the scenario on the Designated_Device rather than replacing device interaction with emulator-only execution, unit tests, mocks, or service-only calls.
5. IF a required interaction cannot be completed, THEN THE E2E_Test_Cycle SHALL record the failed step and stop the cycle.

### Requirement 4: Live NVIDIA request through the application

**User Story:** As a release engineer, I want the cycle to exercise the live NVIDIA API exactly as the application does on the device, so that the result validates the real integration path.

#### Acceptance Criteria

1. WHEN the user submits valid tailoring input with a Runtime_API_Key, THE running application SHALL send the tailoring request through its normal device execution path to the configured Live_NVIDIA_API.
2. THE E2E_Test_Cycle SHALL classify the NVIDIA interaction as live only when the request reaches the configured NVIDIA endpoint and the response is not supplied by a mock, stub, fixture, cached response, or direct test harness substitution.
3. WHEN the Live_NVIDIA_API returns a usable response, THE E2E_Test_Cycle SHALL continue through the application's normal response-handling and resume-generation flow.
4. IF the Live_NVIDIA_API returns an error, times out, rejects the Runtime_API_Key, or returns an unusable response, THEN THE E2E_Test_Cycle SHALL record the service failure and mark the cycle unsuccessful.
5. THE E2E_Test_Cycle SHALL avoid altering application behavior or request handling solely for the purpose of testing the Live_NVIDIA_API.

### Requirement 5: Tailored resume generation

**User Story:** As a release engineer, I want the cycle to verify the application's generated resume, so that a successful service call demonstrates the intended user outcome.

#### Acceptance Criteria

1. WHEN the Live_NVIDIA_API response is accepted by the application, THE E2E_Test_Cycle SHALL reach the application's generated-resume state through the normal device UI flow.
2. WHEN the application produces a Tailored_Resume artifact, THE E2E_Test_Cycle SHALL verify that the artifact exists and has a byte size greater than zero.
3. WHEN the generated resume content is available for inspection, THE E2E_Test_Cycle SHALL verify the scenario-defined Resume_Markers required to demonstrate tailoring, including at least one resume heading, one skills or competency marker, one experience or employment marker, and one tailored job keyword.
4. IF the application does not produce a Tailored_Resume artifact, THEN THE E2E_Test_Cycle SHALL record the missing artifact and mark resume verification unsuccessful.
5. IF a generated resume artifact is empty, unreadable, or missing a required Resume_Marker, THEN THE E2E_Test_Cycle SHALL record the validation failure and mark resume verification unsuccessful.

### Requirement 6: PDF handling

**User Story:** As a release engineer, I want PDF output checked without transferring or inspecting the PDF contents, so that PDF handling remains limited to existence and size verification.

#### Acceptance Criteria

1. WHEN the application produces a PDF artifact, THE E2E_Test_Cycle SHALL verify the PDF artifact exists and has a byte size greater than zero.
2. THE E2E_Test_Cycle SHALL not download PDF artifacts from the Designated_Device for content inspection.
3. IF the application does not produce a PDF artifact, THEN THE E2E_Test_Cycle SHALL record the PDF result as not produced without failing HTML or other tailored-resume verification solely for that reason.

### Requirement 7: Records and optional supplemental validation

**User Story:** As a release engineer, I want a compact record of the device cycle while retaining flexibility for additional diagnostics, so that the cycle is runnable without imposing unnecessary evidence requirements.

#### Acceptance Criteria

1. WHEN an E2E_Test_Cycle completes or stops, THE E2E_Test_Cycle SHALL produce a Test_Run_Record containing the device identity, scenario identifier, non-secret input identifiers, step outcomes, live-service classification, and generated-artifact existence and size results.
2. WHEN an E2E_Test_Cycle is repeated, THE E2E_Test_Cycle SHALL create a distinct Test_Run_Record rather than overwrite a prior record.
3. WHERE Supplemental_Evidence is enabled, THE E2E_Test_Cycle SHALL associate collected evidence with the relevant step or checkpoint without exposing the Runtime_API_Key.
4. WHERE screen recording is enabled, THE E2E_Test_Cycle SHALL store the recording as Supplemental_Evidence and SHALL not require recording for cycle success.
5. WHERE supplemental validation tests are enabled, THE E2E_Test_Cycle SHALL report their results separately from the mandatory device-cycle result and SHALL not require those tests for cycle success.
6. THE E2E_Test_Cycle SHALL not require a final verdict field; the Test_Run_Record SHALL preserve per-step outcomes and the mandatory tailored-resume verification result.

### Requirement 8: Application-code protection

**User Story:** As a project maintainer, I want the test workflow kept separate from application implementation, so that the cycle validates the checked-out application behavior.

#### Acceptance Criteria

1. THE E2E_Test_Cycle SHALL not modify application source code as part of device setup, interaction, live API exercise, or artifact verification.
2. THE E2E_Test_Cycle SHALL limit its own generated files to test records, optional Supplemental_Evidence, and application-generated output in designated test locations.
3. WHEN an E2E_Test_Cycle finishes, THE E2E_Test_Cycle SHALL preserve the Test_Run_Record and any enabled Supplemental_Evidence until an explicit cleanup operation removes them.
